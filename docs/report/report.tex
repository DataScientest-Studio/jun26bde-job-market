\section{Introduction}


\subsection{Motivation}

Online job advertisements provide a valuable source of information about the current labour market. Besides describing individual vacancies, they contain structured and semi-structured information about employers, occupations, locations, working conditions, and publication activity. When collected and analysed systematically, this data can be used to identify broader patterns, such as which job categories are most frequently advertised, which companies are recruiting, where jobs are located, and how common home-office opportunities are.

However, individual job advertisements are temporary and continuously changing. New advertisements appear, existing ones are modified or republished, and others disappear. Analysing the job market therefore requires more than simply retrieving the current search results. The data must be collected repeatedly, preserved over time, transformed into a consistent structure, and made available for further analysis.

The Job Market project addresses this problem by treating job advertisements as a continuously updated data source. Public job data from the German Bundesagentur für Arbeit is collected and processed in an end-to-end data engineering pipeline. The resulting dataset provides the basis for exploring the German job market through statistical analysis, filtering, and visualisation.


\subsection{Project Objectives}

The main task of the Job Market project is to implement an end-to-end data engineering system that collects German job advertisements, preserves the source data, transforms it into a consistent structure, and makes the resulting information available for interactive exploration and analysis. Besides searching and filtering individual vacancies, the system should support analysis of broader job-market characteristics such as job categories, employers, locations, home-office availability, publication activity, and advertisement freshness.

A further task is to make data collection repeatable and observable rather than relying on one-time manual imports. The project therefore includes recurring data collection, persistent storage, an API for accessing the processed data, interactive visualisation, and operational monitoring of the application and ETL process.

The scope is deliberately centred on data engineering rather than machine learning. Job categories are assigned using deterministic rules, and the application is designed as a reproducible local demonstration system rather than as a public production job portal.


\subsection{Our Solution}

Figure~\ref{fig:project-overview} presents the overall architecture of the implemented system.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=0.85\textwidth,height=0.72\textheight,keepaspectratio]{project-overview.png}
	\caption{Overall architecture of the Job Market system.}
	\label{fig:project-overview}
\end{figure}

The system separates data ingestion from interactive data consumption. This separation allows the collection pipeline to operate independently of the user-facing application: job advertisements can be retrieved, transformed, enriched, and persisted without requiring the dashboard or API to be involved in the ingestion process.

The ingestion side is centred on a Python ETL pipeline that retrieves job advertisements from the Bundesagentur für Arbeit API (\cite{arbeitsagentur-api}). The extraction stage preserves the original JSON responses, while the transformation stage converts the source-specific representation into the internal job model, performs enrichment and classification, and prepares the records for persistence. PostgreSQL serves as the authoritative structured data store for the application. After the database has been updated and job freshness has been evaluated, the active advertisements are synchronised to Elasticsearch. The Elasticsearch index therefore represents a rebuildable, search-oriented projection of the PostgreSQL data rather than an independent source of truth.

The runtime side follows a layered application architecture. FastAPI forms the service layer between the data stores and the user interface and exposes job listings, details, filters, and aggregated statistics through HTTP endpoints. Requests without a keyword are handled directly through PostgreSQL. When a keyword is supplied, FastAPI uses Elasticsearch for full-text search and relevance ranking. Elasticsearch returns the matching job reference numbers in ranked order, after which the corresponding job records are retrieved from PostgreSQL while preserving that order. The Dash frontend consumes these endpoints rather than accessing either data store directly.

Data collection is automated with Airflow (\cite{airflow-docs}), while Prometheus, Pushgateway, and Grafana (\cite{prometheus-docs,prometheus-pushgateway,grafana-docs}) provide operational monitoring of the application and ETL process. These supporting components are described in more detail in the following sections. All major services are executed as Docker containers and connected through Docker Compose, providing a reproducible local runtime environment.

\section{Data Collection and ETL Pipeline \label{sec:data-collection}}


\subsection{Data Source}

The project uses the job-search interface of the German Bundesagentur für Arbeit as its single data source. This choice matches the focus on the German labour market and provides structured job advertisements through HTTP endpoints without requiring the reconciliation of schemas from multiple providers. Alternatives such as Adzuna are subject to more restrictive request limits and potential licensing conditions, while The Muse is primarily oriented towards its own international job catalogue. Using a single consistent source therefore allowed the project to focus on the complete data-engineering workflow rather than on source-specific integration problems.

The job-search endpoint returns paginated advertisement lists and supports parameters such as \texttt{was} for the search keyword, \texttt{wo} for an optional location, \texttt{page}, and \texttt{size}. Each result contains a reference number that uniquely identifies the advertisement and can be used to request its complete record through the detail endpoint. The detail response provides the primary input for transformation and includes information such as title, occupation, employer, description, employment conditions, salary, publication and modification dates, external links, and one or more job locations.

A special case occurs when a previously observed advertisement is no longer available. If the detail endpoint returns HTTP 404 together with the source-specific code \texttt{STELLENANGEBOT\_NICHT\_GEFUNDEN}, this is interpreted as evidence that the advertisement no longer exists at the source. This distinction is important for job-freshness tracking because a confirmed disappearance must be distinguished from a temporary request failure.

\subsubsection{Extraction}

The extraction process is shown in the upper row of Figure~\ref{fig:ingestion-pipeline}.

An extraction run can process several search keywords. For each keyword, the first search-result page is requested and its pagination metadata is used to determine the total number of pages. The API reports the maximum number of results and the effective page size, from which the extraction code calculates the required number of requests. Every successfully retrieved page is preserved unchanged as JSON under a keyword-specific directory. This creates a raw archive of the actual search responses rather than retaining only the subsequently transformed records.

The same advertisement may occur in the result sets of several search terms. Reference numbers are therefore deduplicated across all keywords within an extraction run to avoid unnecessary processing. Malformed result entries and advertisements without a valid reference number are skipped. The resulting set of unique references represents the jobs observed during the current search and is also retained for the subsequent job-freshness update.

Full job details are retrieved using the unique reference numbers obtained from the search results. To reduce unnecessary API requests, an existing advertisement is not automatically downloaded again on every run. The extraction code compares the source modification timestamp, \texttt{aenderungsdatum}, with the timestamp already stored for that job. Detail retrieval is required for new advertisements, advertisements whose modification timestamp has changed, and cases in which the timestamps are missing or cannot be compared reliably. Unchanged advertisements can therefore remain in PostgreSQL without repeatedly downloading and processing identical detail records.

A failure to retrieve an individual detail record does not abort the complete extraction. Successful responses are collected in \path{job-details.json}, while failed requests are written separately to \path{job-detail-failures.json} together with the affected reference number and error message. The remaining advertisements can therefore continue through the pipeline, while failed requests remain traceable for diagnosis.

Each extraction run receives its own UTC-timestamped directory under \path{data/raw/arbeitsagentur}. Within this directory, the individual search-result pages are stored under \path{search-results/<keyword>/}, while retrieved detail records and detail-request failures are stored at the run level. For example, a run may create a directory such as \path{data/raw/arbeitsagentur/2026-08-03T11-14-18Z/}. Keeping each run separate preserves the original source data and provides a reproducible record of what was returned by the external service at a particular point in time.


\subsubsection{Transformation}

The transformation stage converts the source-specific JSON representation returned by the Bundesagentur für Arbeit into the internal schema used by the remainder of the application. As shown in Figure~\ref{fig:ingestion-pipeline}, it is positioned between the raw JSON archive and PostgreSQL persistence and produces a cleaned and enriched intermediate dataset.

German field names from the source API are mapped to consistent English names, for example \texttt{referenznummer} to \path{reference_number}, \texttt{stellenangebotsTitel} to \texttt{title}, and \texttt{firma} to \texttt{company}. The same principle is applied to employment conditions, salary information, dates, external links, and employer metadata. This isolates the rest of the application from the terminology and structure of the external API and provides a stable internal representation for persistence and consumption.

Nested structures are normalised during the same process. The source field \texttt{stellenlokationen} may contain several job locations, which are converted into a list of location objects containing postal code, city, region, country, latitude, and longitude. Entry and publication periods are similarly reduced to the relevant start dates used by the internal model. The transformation is designed to tolerate incomplete or malformed source data: missing optional fields become null values, while malformed nested structures or individual location entries are ignored rather than causing the entire transformation to fail.

After structural normalisation, only advertisements containing at least one location in \texttt{DEUTSCHLAND} are retained. Each job is assigned one of the project's standardised categories based on its title and occupation, and missing geographic coordinates are enriched by the location geocoder. Malformed locations encountered during geocoding are counted and reported by the transformation process.

The transformed records are written to \path{clean-jobs.json} under \path{data/processed/arbeitsagentur/<timestamp>/}, using the timestamp inherited from the corresponding extraction run. The archived source responses remain unchanged, preserving a clear distinction between immutable raw input and the cleaned data consumed by the loading stage.

\paragraph{Location Enrichment}

Job advertisements may already contain geographic coordinates for their locations. When both latitude and longitude are available from the source, these values are retained unchanged and the location is marked with \path{coordinates_source = "source"}. Only locations with missing coordinates are passed to the additional geocoding step shown in Figure~\ref{fig:ingestion-pipeline}.

Missing coordinates are resolved using the Nominatim geocoding service (\cite{nominatim-api}) through the \texttt{geopy} library. A query is constructed from the available postal code, city, and country fields. Successful results are stored with \path{coordinates_source = "geocoded"}, while unsuccessful lookups leave the coordinates empty and mark the source as \texttt{"missing"}. Requests are passed through \texttt{geopy}'s \texttt{RateLimiter} to comply with the Nominatim usage policy \cite{nominatim-policy}; the default configuration enforces a one-second delay between requests and retries temporary failures.

To avoid repeated external requests, the geocoder maintains an in-memory cache indexed by the normalised location query. Both successful and unsuccessful lookups are cached, so multiple advertisements referring to the same postal code, city, and country combination normally require only one Nominatim request during an ETL run.

Unsuccessful lookups are also recorded through the \path{failed_geocoding_requests} metric. The metric represents the number of failed geocoding requests in the current ETL run and is subsequently submitted to Prometheus through Pushgateway together with the other ETL metrics.


\paragraph{Job Classification \label{sec:job-classification}}

To support filtering and statistical analysis, each transformed advertisement is assigned to one of the broad job categories shown in Figure~\ref{fig:job-classification}. The categories are deliberately broader than individual job titles so that advertisements with different naming conventions can be compared at an aggregate level. Jobs that do not match any configured category are assigned to \textit{Other}.

\begin{figure}[htbp]
	\centering
	\includegraphics[
	width=\textwidth,
	keepaspectratio
	]{classification.png}
	\caption{Rule-based standardisation of heterogeneous job titles into broad job categories.}
	\label{fig:job-classification}
\end{figure}

Classification is performed during the transformation stage shown in Figure~\ref{fig:ingestion-pipeline}. The classifier combines the job title and occupation fields, normalises the resulting text, and compares it with category-specific keyword lists defined in \path{src/config/settings.py}.

Because an advertisement may contain terms associated with several categories, classification follows a fixed priority order (Figure~\ref{fig:ingestion-pipeline}, right box). The first match determines the category. For example, a position titled \textit{Backend Developer for Machine Learning} is classified as \textit{AI / Machine Learning} rather than \textit{Backend Development}. This keeps the classification deterministic while resolving common ambiguities.

Short keywords require special handling because simple substring matching can produce false positives when an abbreviation occurs inside a longer word. Keywords of three characters or fewer are therefore matched as complete terms using regular-expression boundaries. This applies, for example, to abbreviations such as \texttt{ETL}, \texttt{NLP}, \texttt{LLM}, and \texttt{SRE}.

The approach is intentionally lightweight and transparent, but depends entirely on the configured keywords and the wording of the title and occupation fields. Unrepresented synonyms or uncommon titles may therefore be assigned to \textit{Other}, while advertisements spanning several disciplines are reduced to a single category according to the fixed priority. The resulting categories are suitable for broad exploration and visualisation but should not be interpreted as an authoritative occupational taxonomy.


\subsubsection{Loading}

The loading stage persists the cleaned records produced by the transformation stage into PostgreSQL and completes the ETL process shown in Figure~\ref{fig:ingestion-pipeline}.

Before loading, the required relational schema is created if it does not yet exist. The main \texttt{jobs} table stores the advertisement data, while locations are normalised into the separate \path{job_locations} table because one advertisement may refer to multiple locations.

The reference number supplied by the Bundesagentur für Arbeit is used as the stable identifier of an advertisement and forms the primary key of the \texttt{jobs} table. Date-like values such as publication and modification timestamps are converted into values compatible with the corresponding PostgreSQL column types before insertion.

Jobs are persisted using PostgreSQL's \texttt{INSERT ... ON CONFLICT} mechanism. A previously unseen reference number creates a new row, while an existing reference number causes the stored advertisement to be updated with the latest source data. Re-running the pipeline therefore does not create duplicate advertisements: the same source advertisement continues to correspond to one database row.


\paragraph{Update Strategy}

In addition to the current advertisement data, the loader distinguishes genuine modifications from unchanged republications. A newer \path{publication_date} does not necessarily indicate a changed advertisement, because a job may be republished while its \path{modified_at} value remains unchanged. The decision logic is illustrated in Figure~\ref{fig:job-freshness}.

\begin{figure}[htbp]
	\centering
	\includegraphics[
	width=\textwidth,
	keepaspectratio
	]{job-freshness.png}
	\caption{Detection of job modifications and unchanged republications.}
	\label{fig:job-freshness}
\end{figure}

A changed \path{modified_at} value is interpreted as a genuine modification. If \path{modified_at} remains unchanged while \path{publication_date} changes, the advertisement is treated as an unchanged republication and \path{unchanged_republish_count} is incremented. The original \path{first_publication_date} is retained as the earliest publication date observed by the project.

After a job is inserted or updated, its stored locations are replaced by those in the current cleaned record. Each location is linked to the job through a foreign key with \texttt{ON DELETE CASCADE}.

The job update and location replacement are performed within a database transaction. If part of the operation fails, the transaction is rolled back, preventing partially updated advertisements. Invalid records are logged and skipped while processing continues with the remaining jobs.


\subsection{Elasticsearch Index Synchronisation}

Elasticsearch is maintained as a derived search index rather than as an independent data store. PostgreSQL remains the authoritative source of job data, and the Elasticsearch index is rebuilt from the current database state after each scheduled ETL run. In the Airflow workflow, database loading and the job-freshness update are completed before Elasticsearch synchronisation, ensuring that the index reflects the latest active state of the advertisements.

During synchronisation, all active jobs are selected from PostgreSQL together with the fields required for full-text search and filtering. Because one job may have several rows in the \texttt{job\_locations} table, their city values are aggregated into a single \texttt{cities} array. One Elasticsearch document therefore represents one job advertisement even when the relational record has multiple locations.

The existing index is recreated and the selected jobs are inserted using the PostgreSQL \texttt{reference\_number} as the Elasticsearch document identifier. Only attributes required by the search functionality are copied. The resulting mapping is summarised in Table~\ref{tab:elasticsearch-mapping}.

\begin{table}[htbp]
	\centering
	\begin{tabular}{lll}
		\hline
		\textbf{Field} & \textbf{Elasticsearch type} & \textbf{Purpose} \\
		\hline
		\texttt{reference\_number}     & \texttt{keyword}        & stable job identifier \\
		\texttt{title}                 & \texttt{text}           & full-text search \\
		\texttt{occupation}            & \texttt{text}           & full-text search \\
		\texttt{description}           & \texttt{text}           & full-text search \\
		\texttt{company}               & \texttt{text + keyword} & search and exact representation \\
		\texttt{category}              & \texttt{text + keyword} & search and exact filtering \\
		\texttt{cities}                & \texttt{keyword}        & exact city filtering \\
		\texttt{home\_office\_possible}& \texttt{boolean}        & boolean filtering \\
		\texttt{is\_active}            & \texttt{boolean}        & active-job filtering \\
		\hline
	\end{tabular}
	\caption{Elasticsearch mapping for searchable job advertisements.}
	\label{tab:elasticsearch-mapping}
\end{table}

Fields mapped as \texttt{text} are analysed for full-text queries, whereas \texttt{keyword} fields retain exact values for filtering. Multi-fields are used for \texttt{company} and \texttt{category}, allowing the same value to support both use cases. Lowercase normalisation is applied where case-insensitive exact filtering is required.

Because the index is a rebuildable projection of PostgreSQL, it can be discarded and recreated without loss of application data. Rebuilding it from active jobs also ensures that advertisements no longer considered active are removed from the search index.




\section{Data Modelling and Storage}


\subsection{Storage Strategy}

The project uses a two-layer storage strategy. Raw API responses are preserved unchanged in timestamped JSON directories, providing a lightweight historical archive of individual extraction runs. This makes the source data traceable and allows transformations to be reproduced without introducing the infrastructure and operational complexity of a dedicated data lake. The cleaned JSON produced during transformation serves only as an intermediate ETL artifact.

PostgreSQL stores the transformed application data because job advertisements and locations form a stable relational structure that is frequently filtered, joined, and aggregated. It provides referential integrity, transactions, indexing, and efficient SQL-based analysis while integrating well with Python, SQLAlchemy (\cite{sqlalchemy-docs}), and FastAPI.

A document database such as MongoDB could store the nested source responses directly, but provides little advantage after transformation into the stable relational schema. Preserving the original responses as JSON while storing the structured representation in PostgreSQL therefore provides the required flexibility without operating an additional database system.


\subsection{Relational Data Model}

The transformed data is represented by two related tables. The \texttt{jobs} table stores the attributes of a job advertisement and uses the source reference number as its primary key. The \path{job_locations} table stores geographical information and references the corresponding advertisement through a foreign key. A job may therefore have zero or more locations, while each location belongs to exactly one job.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=0.72\textwidth, height=0.72\textheight, keepaspectratio]{erd.png}
	\caption{Entity--relationship diagram of the job-market database}
	\label{fig:erd}
\end{figure}

Separating jobs and locations avoids duplicating the complete advertisement when a job is associated with several locations. The foreign-key constraint preserves referential integrity, while \texttt{ON DELETE CASCADE} removes dependent locations when a job is deleted. An index on \path{job_locations.reference_number} supports efficient retrieval and joins by advertisement.

Most source-derived attributes are nullable because the API does not provide all information for every advertisement. Application-controlled values, such as the standardised category and freshness state, use defined defaults instead. The source reference number uniquely identifies advertisements and, together with PostgreSQL's \texttt{INSERT ... ON CONFLICT DO UPDATE}, prevents duplicate job rows during repeated ETL runs.




\section{Data Access and Visualisation}


\subsection{FastAPI Backend}

FastAPI was selected as the service layer between PostgreSQL and the user-facing dashboard. The project specification requires an API through which the stored data can be queried, and FastAPI provides a lightweight Python framework that integrates naturally with the rest of the application. The backend is defined in \path{src/api/main.py}, while the individual routes are separated into modules for health checks, job access, and statistics under \path{src/api/routes/}. The application is served by Uvicorn on port 8000.

A central advantage of FastAPI is its support for typed API contracts. Request parameters are declared using Python type annotations and FastAPI's query-parameter definitions. This allows constraints to be expressed directly in the route signature; for example, the job-list endpoint restricts \texttt{limit} to values between 1 and 100 and requires a non-negative \texttt{offset}. Optional filters such as keyword, city, company, home-office availability, and category are also explicitly typed. Response structures are defined using Pydantic models such as \texttt{JobModel}, \texttt{JobLocationModel}, and \texttt{JobDetailModel}. These models distinguish required values from nullable source fields and provide a stable JSON contract independently of the internal SQL query results.

The same type information is used for validation and documentation. FastAPI validates incoming path and query parameters before the route logic is executed, while Pydantic validates the data used to construct response objects. Declared response models also ensure that the structure exposed through the API corresponds to the intended public representation rather than to arbitrary database rows. Parameter descriptions, examples, response schemas, and documented error responses are incorporated automatically into the generated OpenAPI specification.

FastAPI consequently provides interactive Swagger documentation without requiring a separate documentation application. When the backend is running, the interface is available at \path{http://127.0.0.1:8000/docs}, where the available Health, Jobs, and Statistics endpoints can be inspected and tested directly. This was particularly useful during development because API parameters and responses could be verified independently of the Dash frontend.

The API also establishes a clear boundary between data access and presentation. PostgreSQL is accessed by the backend through the shared database layer, whereas the Dash application does not query the database directly. Instead, the frontend sends HTTP requests to FastAPI and renders the returned JSON data. In the Docker Compose environment, this separation is reflected by the dedicated \texttt{backend} and \texttt{frontend} services, with the frontend configured to use \path{http://backend:8000}. As a result, database queries, filtering rules, validation, and statistical aggregation remain on the backend side, while Dash is responsible for user interaction and visualisation.


\subsection{Job API}

The main job-access endpoints are implemented in \path{src/api/routes/jobs.py}. The collection endpoint \path{/jobs} provides a compact representation of currently active advertisements, while \path{/jobs/{reference_number}} returns the complete stored representation of one advertisement together with all of its associated locations. The list representation contains the reference number, title, company, occupation, salary information, category, and a representative location with its coordinates; the detail representation additionally exposes the description, employment conditions, dates, external links, freshness information, and the complete list of locations.

The \path{/jobs} endpoint supports several optional search and filter parameters that can be combined within the same request. The \texttt{city} parameter restricts the result to jobs having a location whose city matches the supplied value case-insensitively, while \texttt{company} supports matching company names. The boolean \path{home_office} parameter filters according to the source field describing home-office availability, and \texttt{category} selects one of the standardised job categories introduced during transformation. The \texttt{keyword} parameter activates the full-text search path described in the following subsection. Only advertisements whose \path{is_active} state is true are returned by the list endpoint.

Pagination is implemented through the \texttt{limit} and \texttt{offset} query parameters. The default page size is 20 jobs, values between 1 and 100 are accepted, and the default offset is zero. For requests without a full-text keyword, results are ordered by publication date in descending order and then by reference number, which provides deterministic ordering when several advertisements share the same publication date. Keyword searches instead preserve the relevance ordering produced by Elasticsearch, as described in the following subsection. If the offset exceeds the available result set, the endpoint returns an empty list rather than an error.

Figure~\ref{fig:swagger-jobs} shows the collection endpoint in the automatically generated Swagger interface. The displayed controls correspond to the full-text search, structured filters, and pagination parameters described above and can be combined within a single request.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=1\textwidth]{swagger-jobs.png}
	\caption{Swagger interface for the \texttt{GET /jobs} endpoint, showing full-text search, structured filters, and pagination parameters.}
	\label{fig:swagger-jobs}
\end{figure}

The detail endpoint \path{/jobs/{reference_number}} uses the stable source reference number as a path parameter. It retrieves the main job row and all related rows from \path{job_locations}, combining them into a \texttt{JobDetailModel}. Unlike the list endpoint, the lookup is performed directly by reference number and does not restrict the result to currently active advertisements. An unknown reference number produces HTTP~404, while database-unavailability errors are exposed as HTTP~503 responses.

Figure~\ref{fig:swagger-job} illustrates a successful request to the detail endpoint. The reference number is supplied as a path parameter, and the returned HTTP~200 response contains the complete job representation.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=1\textwidth]{swagger-job.png}

	\label{fig:swagger-job}
\end{figure}

This API contract is also the interface consumed by the Dash frontend. Filtering, pagination, and database access therefore remain backend responsibilities, while the dashboard only submits the selected parameters and renders the returned results.

Since a job advertisement may contain several locations, the compact job response selects a representative location for display. If a city filter is supplied, a matching location is preferred, with locations containing valid coordinates taking precedence. Without such a preference, a location with valid coordinates is selected where possible. The detailed job endpoint is unaffected by this simplification and returns all locations associated with the advertisement.

\subsection{Full-Text Search and Structured Filtering}

The job-search endpoint distinguishes between a free-text search criterion and structured filters. The API parameter \texttt{keyword} represents a relevance-oriented search, whereas parameters such as \texttt{city}, \texttt{company}, \texttt{home\_office}, and \texttt{category} restrict which advertisements are eligible for the result set. The API parameter name \texttt{keyword} should therefore not be confused with the Elasticsearch \texttt{keyword} field type described in the previous section.

Figure~\ref{fig:elasticsearch-search} summarises the two search paths implemented by the backend. Requests without a free-text keyword are handled entirely by PostgreSQL. When a keyword is supplied, Elasticsearch performs the full-text search and relevance ranking and returns the matching job reference numbers. FastAPI then retrieves the corresponding job records from PostgreSQL while preserving the Elasticsearch ranking.

\begin{figure}[htbp]
	\centering
	\includegraphics[
	width=\textwidth,
	keepaspectratio
	]{elasticsearch.png}
	\caption{Job-search routing and Elasticsearch-based full-text search with relevance ranking.}
	\label{fig:elasticsearch-search}
\end{figure}

For keyword searches, Elasticsearch uses a \texttt{multi\_match} query across the title, occupation, company, category, and description fields. The fields are weighted according to their expected relevance: title receives the highest boost, followed by occupation, category, company, and description. This makes a match in the job title more influential than the same term occurring only in the description.

Structured filters remain the responsibility of PostgreSQL. They can be applied together with the reference numbers returned by Elasticsearch, allowing full-text relevance ranking to be combined with constraints such as location, company, category, or home-office availability. PostgreSQL therefore remains the authoritative source of job data, while Elasticsearch acts as a specialised search index.


\subsection{Statistics API}

In addition to individual job retrieval, the FastAPI backend exposes a set of read-only statistical endpoints under the \path{/statistics} prefix. These endpoints perform SQL aggregations directly on PostgreSQL and provide the data consumed by the Statistics page of the Dash frontend.

The \path{/statistics/overview} endpoint returns a compact summary of the stored dataset. Its response contains the total number of jobs, the number of distinct companies, the number of distinct locations, and the earliest and latest publication dates available in the database. Distinct locations are determined from the combination of city, region, and country rather than from the number of rows in the location table.

The \path{/statistics/companies} endpoint groups advertisements by company and returns the employers with the highest numbers of stored jobs. Companies with missing or empty names are excluded. The number of returned companies can be controlled using the \texttt{limit} parameter, which defaults to 20 and accepts values between 1 and 100. The dashboard currently requests the ten highest-ranked companies.

Similarly, \path{/statistics/locations} aggregates the location table and returns cities ordered by the number of distinct associated job advertisements. Each response item contains the city, region, country, and job count. Counting distinct reference numbers is important because one advertisement may contain more than one location row. The endpoint also supports a configurable result limit and is used by the dashboard to display the most frequently occurring locations.

The \path{/statistics/home-office} endpoint summarises the nullable \path{home_office_possible} field into three groups: \texttt{possible}, \path{not_possible}, and \texttt{unknown}. Treating null values separately avoids interpreting missing source information as a negative answer. The \path{/statistics/categories} endpoint groups all stored advertisements by the standardised category assigned during transformation and returns the corresponding job count for each category. These values are later visualised as the home-office and category distributions in Dash.

The \path{/statistics/publication-trends} endpoint provides a temporal view of the stored advertisements. It groups jobs by the month of their \path{first_publication_date}, excludes records for which this date is unavailable, and returns the resulting months and job counts in chronological order. The Dash frontend uses these values to construct the publication-trend chart shown in the following subsection. Figure~\ref{fig:swagger-trends} illustrates this endpoint and an example of its returned monthly aggregation.

\section{Deployment and Automation}


\subsection{Containerisation}

Docker is used to provide an isolated and reproducible runtime environment for the project components. Rather than maintaining separate Python images for every application service, the backend, frontend, and manual data-update service are built from the same root \path{Dockerfile}. The image is based on \path{python:3.12-slim}, installs the common project dependencies, copies the source code into \path{/app}, and configures \path{/app} as the Python module path. This ensures that the three services execute the same application code and dependency versions while still performing different roles.

The distinction between these services is introduced at runtime by Docker Compose through different commands and environment variables. The backend starts Uvicorn with the FastAPI application on port 8000, the frontend starts the Dash application on port 8050, and the \texttt{data-update} service executes the ETL module. Reusing the same application image avoids duplicating nearly identical Dockerfiles and reduces the risk that the API, dashboard, and ETL environments diverge from one another.

Airflow uses a separate image defined by \path{airflow/Dockerfile}. It extends the official \path{apache/airflow:3.3.0} image, installs both the project and Airflow-specific dependencies, and copies the application source and DAG definitions into the Airflow environment. A separate image is appropriate here because Airflow requires its own runtime, command-line tools, web interface, scheduler components, and directory conventions.

Infrastructure components do not require custom project images. PostgreSQL, Prometheus, Pushgateway, Alertmanager, and Grafana are instantiated directly from their respective official images. Persistent state is kept outside the container filesystems through Docker volumes: PostgreSQL data, archived ETL data, Prometheus time-series data, and Grafana state therefore survive container recreation. Containerisation consequently separates application execution from persistent data and makes the complete environment reproducible without installing the individual services directly on the host system.


\subsection{Docker Compose Deployment}

Docker Compose defines the runtime topology of the system and connects the individual containers through Docker's internal service network. Figure~\ref{fig:docker-deployment} shows the principal application and data-flow relationships. The same ETL implementation can be executed automatically by Airflow or manually through the \path{data-update} service.

The \texttt{postgres} service provides the authoritative relational data store and persists its database files in the \path{postgres_data} volume. A health check based on \path{pg_isready} prevents dependent application services from starting before the database is ready to accept connections.

The \texttt{backend} service runs FastAPI and communicates with PostgreSQL through the internal Docker hostname \texttt{postgres}. The \texttt{frontend} service runs Dash and accesses the backend over HTTP using \path{http://backend:8000}; it does not connect directly to the database. Ports 8000 and 8050 expose the API and dashboard respectively to the host machine.

Two execution paths are available for data ingestion. The \path{data-update} service provides an on-demand ETL environment and can be invoked manually when a new collection run is required. The \texttt{airflow} service provides the scheduled execution path: its DAG executes extraction, transformation, loading, and job-freshness updates automatically. Both services access PostgreSQL and share the \path{job-market-data} volume used for the archived and processed JSON files.

The remaining services provide observability. Prometheus collects application and ETL metrics, while Pushgateway acts as an intermediary for metrics produced by the periodically running ETL tasks, which cannot be scraped continuously like a long-running web service. Grafana uses Prometheus as its datasource to provide operational dashboards, and Alertmanager receives alerts generated from Prometheus alerting rules. These auxiliary monitoring connections are omitted from Figure~\ref{fig:docker-deployment} for readability and are described in more detail in the monitoring subsection.


\subsection{Persistent Storage and Service Dependencies}

Container filesystems are ephemeral by design, so data that must survive container recreation is stored in named Docker volumes. PostgreSQL uses the \path{postgres_data} volume for its database files, making the relational dataset independent of the lifecycle of the \path{postgres} container. The extraction and transformation pipeline uses the \path{job-market-data} volume mounted at \path{/app/data}; this volume is shared by the manual \path{data-update} service and Airflow so that both execution paths operate on the same archived raw data and processed JSON files.

The monitoring services maintain their state in separate volumes. Prometheus stores its collected time-series data in \path{prometheus_data}, while Grafana uses \path{grafana_data} for its application state. In addition, Prometheus configuration, alert rules, Grafana datasource configuration, and dashboard definitions are mounted from version-controlled project files. This separates persistent runtime data from declarative configuration and allows the monitoring environment to be recreated consistently.

Service startup dependencies are defined through Docker Compose. The PostgreSQL service includes a health check based on \path{pg_isready}. Both the FastAPI backend and the ETL-related services wait for PostgreSQL to reach the healthy state before starting, preventing database operations from being attempted while the server is still initialising. The \path{data-update} and \path{airflow} services additionally depend on Pushgateway being started because they can publish ETL metrics to it. The frontend depends on the backend, while Grafana depends on Prometheus. These latter dependencies establish startup ordering but do not perform the same readiness validation as the PostgreSQL health check.

Where external browser access is required only from the development machine, ports are bound explicitly to the loopback interface. The FastAPI backend, Dash frontend, Airflow interface, Prometheus, Pushgateway, and Grafana are exposed through \path{127.0.0.1}, making them reachable from the host without publishing them on all network interfaces. PostgreSQL is currently exposed through port 5432 without this restriction, and Alertmanager is similarly published on port 9093. These bindings reflect the project's local development and demonstration environment rather than a hardened production network configuration.


\subsection{ETL Orchestration with Airflow}

Apache Airflow is used to automate the recurring execution of the ingestion pipeline. The DAG is defined in \path{airflow/dags/job_market_etl.py} and reuses the same extraction, transformation, loading, and freshness-tracking functions that can also be executed outside Airflow. Airflow therefore acts as the orchestration layer rather than implementing a separate ETL pipeline.

The workflow begins with the \texttt{extract} task, which calls the extraction logic using the configured default search keywords. It returns two outputs: the path of the timestamped raw-data directory and the set of reference numbers observed during the current search. The raw-data path is passed to the \texttt{transform} task, which creates the cleaned and enriched JSON representation. The resulting processed-data path is then passed to the \texttt{load} task, which persists the transformed advertisements and their locations in PostgreSQL.

After loading has completed, the \path{update_freshness} task compares the reference numbers observed during extraction with the jobs already stored in the database. This final step updates the observation state of advertisements and allows jobs that are no longer found during a complete collection run to be marked accordingly. Passing both the observed reference numbers and the completed load result to this task ensures that freshness information is not updated before the current dataset has been successfully processed.

The resulting task dependency chain is therefore \path{extract $\rightarrow$ transform $\rightarrow$ load $\rightarrow$ update_freshness}. Airflow manages these dependencies explicitly and executes a downstream task only after its required upstream output is available. The DAG is scheduled with the cron expression \path{0 6 * * *}, causing one automated collection run every day at 06:00. The configuration \path{catchup=False} prevents Airflow from creating historical runs for scheduling intervals that were missed before the DAG became active or while the environment was offline.

Airflow itself runs as a dedicated Docker Compose service. Its custom image is defined in \path{airflow/Dockerfile} and is based on the official \path{apache/airflow:3.3.0} image. The project dependencies, application source code, and DAG definitions are copied into this image so that the Airflow tasks can directly import the shared ETL modules. The service runs \path{airflow standalone}, connects to the same PostgreSQL database as the rest of the application, shares the \path{job-market-data} volume used for generated JSON files, and exposes its web interface on port 8080 for local inspection of DAG runs and task status.

\subsection{Monitoring Architecture}

The project includes a monitoring stack for observing both the continuously running backend and the periodically executed ETL pipeline. The monitoring architecture is shown in Figure~\ref{fig:monitoring-architecture}. Metrics produced by the long-running FastAPI backend can be scraped directly, whereas the ETL process exists only for the duration of a scheduled run and therefore publishes its latest metrics through Pushgateway.

	\centering
	\includegraphics[
	width=\textwidth,

	]{monitoring.png}
	\caption{Monitoring architecture using Prometheus, Pushgateway, Grafana, and Alertmanager, with Slack shown as an optional external notification channel. (The faded connection to Slack represents a possible notification integration rather than a currently configured project component.)}

Application metrics are defined in \path{src/monitoring/metrics.py} using the Prometheus Python client. The backend records the number and outcome of job-search requests, their execution duration, and the number of database connections currently in use. Additional instrumentation records requests to the Bundesagentur für Arbeit API, including request duration, success or failure, and whether the most recent source request succeeded. FastAPI exposes these metrics through the \path{/metrics} endpoint, which is mounted directly into the application.

Prometheus acts as the central collection and time-series storage component. Its configuration scrapes the FastAPI backend and Pushgateway every 15 seconds and evaluates alerting rules once per minute. Direct scraping is appropriate for the backend because it is a continuously running service whose current metric state is always available. The collected time series can subsequently be queried using PromQL by dashboards and alerting rules.

The ETL pipeline requires a different approach because it terminates after each scheduled execution. Metrics exposed only inside the ETL process would disappear before Prometheus could reliably scrape them. The ETL therefore uses a separate Prometheus registry and pushes the latest values to Pushgateway after a successful run. These values include \path{etl_runtime_seconds}, the timestamp of the last successful execution in \path{etl_last_success_unixtime}, and the number of failed geocoding requests in \path{failed_geocoding_requests}. Prometheus then scrapes Pushgateway in the same way as a persistent target.

Grafana provides the visual monitoring layer and uses Prometheus as its configured datasource. The provisioned Job Market dashboard displays operational information from both monitoring paths, including job-search request activity, the 95th-percentile search duration, active database connections, the duration of the latest ETL run, the time elapsed since the last successful ETL execution, and the number of geocoding failures. Grafana therefore does not collect metrics itself; it queries and visualises the time series stored by Prometheus.

Alertmanager provides the final component of the monitoring path. Prometheus currently defines an alert named \texttt{ETLNotSuccessfulForTooLong}, which becomes eligible to fire when the recorded last successful ETL execution is more than 26 hours old and the condition remains true for 30 minutes. This threshold allows two hours of tolerance beyond the daily ETL schedule. Firing alerts are forwarded from Prometheus to Alertmanager, which is responsible for grouping and routing notifications. In the current project, Alertmanager is integrated into the monitoring stack, while an external notification channel is not configured. A typical production extension would connect an Alertmanager receiver to a collaboration service such as Slack through an incoming webhook, allowing operational alerts to be delivered automatically to a team channel.


\subsection{Collected Metrics}

The monitoring instrumentation is implemented in \path{src/monitoring/metrics.py} and covers several parts of the application rather than only the FastAPI service. Metrics are grouped according to the external data source, database access, interactive job searches, and periodic ETL execution. This makes it possible to distinguish failures of the source API from problems in the application itself and to observe both continuously running and scheduled processes.

Requests to the Bundesagentur für Arbeit are monitored through three related metrics. \path{arbeitsagentur_requests_total} counts successful and failed requests and distinguishes the API operation through labels, while \path{arbeitsagentur_request_duration_seconds} records their duration as a histogram. The gauge \path{arbeitsagentur_api_up} records whether the most recent monitored request succeeded. Together, these values provide an indication of source availability and allow slow external requests to be distinguished from delays introduced by the local application. These metrics are collected by Prometheus but are not included in the Grafana view shown below.

Database utilisation is represented by the \path{active_database_connections} gauge. The value is incremented when the application enters a monitored PostgreSQL connection and decremented when the connection is released. This provides a simple indication of concurrent database activity and can help relate increases in API traffic to pressure on the persistence layer.

Interactive use of the job API is monitored through \path{job_search_requests_total} and \path{job_search_duration_seconds}. The request counter distinguishes successful and failed searches, while the histogram records the execution time of each job search. In Grafana, the counter is converted into request activity over time, and the histogram buckets are used to calculate the 95th-percentile search duration. These metrics make it possible to observe both workload and responsiveness rather than relying only on a simple request count.

Metrics for the periodic pipeline describe the outcome of the most recent ETL execution. \path{etl_runtime_seconds} stores its total duration, while \path{etl_last_success_unixtime} records the Unix timestamp of the latest successful run. Grafana derives the displayed \path{Time Since Last Successful ETL} value from this timestamp. The gauge \path{failed_geocoding_requests} stores the number of unsuccessful Nominatim lookups in the latest ETL run. Gauges are used for these ETL values because each scheduled process terminates after execution and the intention is to preserve the state of the latest run through Pushgateway rather than maintain process-local counters.

\subsection{Monitoring Periodic ETL Jobs}

Monitoring a periodically executed ETL process differs from monitoring a continuously running web service. The FastAPI backend remains active and exposes its current metrics through the \path{/metrics} endpoint, allowing Prometheus to scrape it at regular intervals. An ETL process, in contrast, exists only for the duration of a scheduled execution and terminates after the pipeline has finished. If Prometheus attempted to scrape the process directly, it could easily miss the short period during which the metrics were available.

Pushgateway is therefore used as an intermediary for ETL metrics. During an ETL run, the application records values such as the total execution time, the timestamp of the latest successful run, and the number of failed geocoding requests. After successful completion, these values are pushed to Pushgateway under the job name \path{job-market-etl}. Pushgateway remains continuously available after the ETL process has terminated, so Prometheus can retrieve the most recently published values during its normal scrape cycle.

The ETL metrics are implemented as gauges in a dedicated Prometheus registry because they describe the state of the latest run rather than continuously increasing values. For example, \path{etl_runtime_seconds} is replaced by the duration of the newest execution, \path{etl_last_success_unixtime} is updated to the current time after a successful run, and \path{failed_geocoding_requests} is reset at the beginning of each execution before new failures are counted. This design allows Grafana and Prometheus alerting rules to inspect the latest ETL state even when no ETL process is currently running.


\subsection{Error Handling}

Error handling is implemented at several layers so that failures of individual external services or records do not unnecessarily terminate the complete application. Requests to the Bundesagentur für Arbeit may fail because of network errors, timeouts, or unsuccessful HTTP responses. Such failures are logged by the extraction process. Where possible, processing continues with other search pages, keywords, or advertisements rather than discarding the complete extraction run.

Job-detail retrieval is handled independently for each reference number. Successfully retrieved details are written to \path{job-details.json}, while advertisements whose detail request fails are recorded separately in \path{job-detail-failures.json} together with the corresponding reference number and error information. This preserves traceability of incomplete extraction runs while allowing successfully downloaded advertisements to proceed through transformation and loading. During freshness checks, a temporary request failure likewise does not cause a previously active job to be marked inactive; its state is left unchanged until its existence can be verified reliably.

Database failures are translated into explicit application-level errors. The shared database layer raises a \texttt{DatabaseUnavailableError} when PostgreSQL cannot be accessed, and the relevant FastAPI job and statistics endpoints convert this condition into HTTP~503 \textit{Service Unavailable} responses. This distinguishes temporary infrastructure failure from cases such as an unknown job reference, for which the detail endpoint returns HTTP~404.

The Dash frontend handles these API failures visibly rather than presenting them as empty results. If the job-list request cannot be completed, the result area displays the message \textit{``The job API is currently unavailable.''} and no job markers are shown on the map. If loading an individual job fails, the details dialog displays a corresponding error message. The user can therefore distinguish an actual search with no matching jobs from a technical failure of the backend or database.

Location enrichment is designed to tolerate failures of the external Nominatim service. Geocoding requests are rate-limited and retried, and exceptions are swallowed after the configured retries so that one unresolved location does not stop the transformation of the remaining advertisements. Locations for which no coordinates can be obtained remain stored without coordinates, while unsuccessful lookups increment the \path{failed_geocoding_requests} metric.

Finally, ETL failures are made observable through the monitoring design. The runtime and last-success metrics are updated only after a complete ETL execution returns successfully. Consequently, a failed run leaves the previous \path{etl_last_success_unixtime} unchanged, allowing Prometheus to detect that no successful update has occurred within the expected interval. The corresponding alert can then be forwarded to Alertmanager. Failure to publish metrics to Pushgateway is itself logged but does not invalidate an otherwise successful ETL run.

\section{Results and Evaluation}


\subsection{Achieved Results}

At the current stage, the project provides a functional end-to-end data-engineering system for collecting, processing, storing, and exploring German job advertisements. The implemented workflow covers the complete path from an external data source to a user-facing analytical application rather than demonstrating the individual technologies only in isolation.

The ingestion pipeline can retrieve paginated job-search results for multiple configured keywords from the Bundesagentur für Arbeit, identify unique advertisements, retrieve their detailed records, and preserve the source responses in timestamped raw-data archives. The transformation stage converts the German source schema into a consistent internal representation, normalises locations, enriches missing coordinates through geocoding, and assigns broad technical job categories. The resulting records can be loaded repeatedly into PostgreSQL without creating duplicate jobs, while changes, disappearance, reappearance, and repeated republication can be tracked across subsequent collection runs.

The stored data is made available through a FastAPI backend with endpoints for health checks, job search, individual job details, and statistical aggregation. Jobs can be filtered by keyword, city, company, home-office availability, and standardised category, with pagination used to control result size. The Dash frontend consumes these endpoints and provides an interactive job-search interface combining result cards, detailed job information, and a geographical map with category-based markers. A separate Statistics view provides aggregated information about employers, locations, home-office availability, job categories, and publication trends.

The pipeline can operate automatically through the Airflow DAG, which executes extraction, transformation, loading, and freshness tracking every day at 06:00. The complete runtime environment is containerised with Docker Compose and combines PostgreSQL, FastAPI, Dash, Airflow, and the monitoring services in a reproducible multi-service setup. Persistent Docker volumes preserve both the relational database and generated extraction data independently of individual container lifecycles.

Operational behaviour is observable through Prometheus metrics covering source-API requests, job-search activity and duration, database connections, ETL runtime and recency, and failed geocoding requests. Periodic ETL metrics remain available through Pushgateway after the ETL process terminates, while Grafana provides a combined view of application and pipeline behaviour. Prometheus alerting rules and Alertmanager additionally provide the basis for detecting missed or excessively delayed ETL executions.

Overall, the implemented system fulfils the central data-engineering objectives of the project: automated data acquisition, historisation of source data, relational storage, API-based data access, interactive visualisation, workflow orchestration, containerised deployment, and operational monitoring. The result is not intended to be a production-scale job portal, but it demonstrates how the individual components can be combined into a coherent and reproducible data platform.


\subsection{Technical Decisions}

PostgreSQL was preferred over using JSON files as the application database because the transformed data has a stable relational structure and must support reliable filtering, joins, aggregation, and repeated updates. JSON remains useful for preserving raw extraction results and intermediate processed data, but querying those files directly from the application would provide weaker consistency guarantees and make incremental updates considerably more difficult. PostgreSQL additionally provides primary and foreign keys, transactions, indexes, and conflict-aware upserts, which are directly useful for the job and location model used by the project.

FastAPI was selected as the access layer between PostgreSQL and the frontend. Its integration with Python type annotations and Pydantic makes request validation and response contracts explicit, while OpenAPI and Swagger documentation are generated automatically. More importantly from an architectural perspective, the API prevents the Dash application from depending directly on the database schema. Filtering, statistics, error handling, and persistence-related logic remain in the backend, allowing the frontend to consume a stable HTTP interface instead of executing SQL itself.

Dash was chosen for the user-facing application because the project is primarily concerned with data engineering and analytical visualisation rather than general-purpose web development. It allows the search interface, interactive Plotly charts, and geographical map to be implemented entirely in Python and integrates naturally with the FastAPI responses. The trade-off is that Dash provides less flexibility than a dedicated JavaScript frontend for complex user-interface behaviour, but this additional complexity was not required for the intended analytical use case.

Raw and processed data are deliberately stored separately. Timestamped raw JSON preserves the responses received from the external source and makes individual ingestion runs traceable, while the processed JSON represents the deterministic result of transformation before persistence. This separation makes debugging and reprocessing possible without repeatedly contacting the external API. It also prevents transformation logic from destroying or replacing the original source representation. PostgreSQL then serves as the operational structured representation rather than as an archive of the unmodified API responses.

Docker Compose was selected to make the multi-service environment reproducible on a development machine. PostgreSQL, FastAPI, Dash, Airflow, Prometheus, Pushgateway, Alertmanager, and Grafana can be started with consistent dependencies, networking, configuration, and persistent volumes without requiring each component to be installed directly on the host. Docker Compose is well suited to the scale and educational purpose of the project, although it does not provide the distributed scheduling, automatic scaling, or high-availability mechanisms that would be expected from a production orchestration platform.

Airflow was selected for recurring data-flow automation because the ingestion process consists of explicit dependent stages rather than a single scheduled command. The DAG expresses the dependency chain \path{extract $\rightarrow$ transform $\rightarrow$ load $\rightarrow$ update_freshness}, provides execution history and task-level visibility, and schedules the workflow once per day at 06:00. A simpler scheduler such as cron could execute the pipeline, but Airflow makes task dependencies and individual runs observable and provides a clearer foundation for extending the workflow with retries or additional processing steps.

Prometheus and Grafana were added to provide operational visibility rather than business analytics. Prometheus offers a suitable model for collecting counters, gauges, and latency histograms from the continuously running backend, while Pushgateway solves the different monitoring requirements of the short-lived ETL process. Grafana provides a convenient interface for correlating metrics such as job-search activity, response duration, database connections, ETL runtime, and ETL freshness. This monitoring stack introduces additional services and configuration, but it allows the project to demonstrate whether the pipeline and application are operating correctly rather than relying solely on logs or manual inspection.


\subsection{Limitations}

The collected dataset does not represent the complete German labour market. The project uses the Bundesagentur für Arbeit as its only job-data source, and the regularly scheduled ingestion is further restricted by the configured search keywords. Advertisements published exclusively through other job portals or company career pages are therefore absent. Statistical results should consequently be interpreted as characteristics of the collected sample rather than as exhaustive labour-market statistics. In addition, individual source fields such as salary, home-office availability, or location information are frequently nullable, which limits analyses based on those attributes.

The temporal information has similar constraints. Publication dates supplied by the source describe the advertisements contained in the current dataset but do not provide a complete historical census of the market. Project-generated fields such as \path{first_seen}, \path{last_seen}, modification counts, and reappearance counts only accumulate from the point at which the pipeline begins observing an advertisement. Reliable conclusions about long-term advertisement lifetimes or repeated republication therefore require the system to operate continuously over a sufficiently long observation period.

Job classification is based on deterministic keyword rules applied to the title and occupation. This makes the classification transparent and reproducible, but it cannot fully capture semantic context, uncommon terminology, or positions spanning several disciplines. The fixed priority order also reduces advertisements to one category even when several categories could reasonably apply. The resulting categories are therefore suitable for filtering and exploratory statistics but should not be interpreted as an authoritative occupational taxonomy.

The Elasticsearch deployment is intentionally simple and designed for the scale of the project. It runs as a single node with no replicas, and its index is rebuilt completely after each scheduled ingestion once the PostgreSQL load and job-freshness update have completed successfully. This provides deterministic synchronisation for the current dataset but would become inefficient at substantially larger scale. Recreating the index also introduces a short interval in which full-text search may be unavailable or incomplete during synchronisation. A larger production system would therefore benefit from incremental indexing or an atomic index-replacement strategy rather than rebuilding the active index in place.

Location enrichment introduces another external dependency. Coordinates supplied by the Bundesagentur für Arbeit can be used directly, but missing coordinates are resolved through the external Nominatim service. Rate limiting, retries, and caching reduce unnecessary requests, yet geocoding can still fail because a location is incomplete, ambiguous, or temporarily unavailable from the service. Such jobs remain usable in the database but cannot necessarily be represented accurately on the geographical map.

Automated testing is currently limited to selected application logic, particularly the deterministic job classifier; broader API, ETL, persistence, and integration testing remains future work.

Finally, the deployment is primarily designed for a local demonstration and development environment. Docker Compose provides reproducibility and service isolation, but the project does not implement distributed deployment, horizontal scaling, or high availability. Several services are deliberately exposed only through localhost bindings, and Elasticsearch authentication and TLS are disabled for simplicity. The FastAPI job and statistics endpoints likewise have no user authentication or authorisation layer. These choices are appropriate for the current project scope but would require additional security, deployment, and operational measures before the system could be exposed as a public production service.


\subsection{Possible Improvements}

The Elasticsearch-based full-text search could be refined further as usage data becomes available. The current field boosts are deliberately chosen from the expected importance of title, occupation, company, category, and description, but relevance could later be evaluated and tuned against observed search queries and user-selected results. German-language analyzers could improve linguistic normalisation and stemming for the predominantly German advertisements, while fuzzy matching and autocomplete could make the search more tolerant of spelling errors and incomplete queries. On the indexing side, the current complete rebuild after each scheduled ingestion could be replaced by incremental updates, or by rebuilding a versioned index and switching an alias atomically, to reduce unnecessary indexing work and avoid temporary search disruption as the dataset grows.

The dataset could also be broadened by integrating additional job-data sources. The current system relies exclusively on the Bundesagentur für Arbeit, which limits both market coverage and the available attributes. Additional APIs or carefully selected job portals could provide advertisements that are absent from the current source and potentially enrich fields such as salary or company information. This extension would, however, require source-specific extraction logic, schema reconciliation, duplicate detection across providers, and a strategy for identifying the same advertisement when reference numbers differ between sources.

Job classification could be improved beyond the current deterministic keyword rules. A more sophisticated approach could consider the complete job description, use linguistic preprocessing or semantic embeddings, or apply a supervised classification model trained on manually labelled advertisements. Such an approach could recognise synonyms and less conventional job titles more reliably and could potentially represent positions that span several technical disciplines. The existing rule-based classifier would nevertheless remain useful as a transparent baseline against which a more advanced method could be evaluated.

The publication-trend and job-freshness functionality could be extended through a substantially longer observation period. The system already records publication information, modification history, disappearance, reappearance, and repeated republication, but the analytical value of these fields increases as more scheduled runs accumulate. Long-term operation would make it possible to analyse typical advertisement lifetimes, repeated republication patterns, and changes in hiring activity over several months rather than relying mainly on publication dates supplied by the source.

Automated testing should also be expanded before the system is treated as production-ready. The current tests cover the basic test infrastructure and selected classification behaviour, but important components such as the Arbeitsagentur client, transformation logic, PostgreSQL persistence, FastAPI endpoints, and failure scenarios require broader automated coverage. Integration tests involving PostgreSQL and the external-service boundaries would complement the existing unit tests and provide greater confidence in changes to the end-to-end pipeline.

For deployment beyond a local demonstration environment, further work would also be required in areas such as authentication, secret management, network exposure, TLS termination, and scalable hosting. Docker Compose is appropriate for the current reproducible local setup, but a publicly accessible service would require additional security and operational controls.




\section{Conclusion}

This project developed an end-to-end data-engineering system for collecting and analysing German job advertisements from the Bundesagentur für Arbeit. The implemented solution covers the complete data lifecycle: advertisements are extracted through the external API, archived as raw data, transformed and enriched, stored in PostgreSQL, exposed through FastAPI, and presented through an interactive Dash application. Airflow automates the recurring ETL workflow, while Docker Compose provides a reproducible multi-service environment and Prometheus, Pushgateway, Grafana, and Alertmanager provide operational monitoring.

The principal objectives of the project were therefore achieved. The resulting application can perform scheduled data acquisition, maintain structured and historical information about job advertisements, provide filtered and aggregated access to the collected data, and make the results available through both analytical visualisations and an interactive job-search interface. The system also demonstrates how failures, changing source data, persistence, service dependencies, and short-lived batch processes can be handled within one coherent architecture.

From a data-engineering perspective, the project combines API integration, ETL design, relational data modelling, data quality and enrichment, workflow orchestration, containerisation, backend development, and observability rather than treating these topics as isolated exercises. An important outcome was that building a useful data pipeline requires more than successfully transferring data from a source into a database. Repeated collection introduces questions of idempotency, missing and changing records, source reliability, traceability, and monitoring. Designing for these concerns from the beginning was therefore one of the most important lessons of the project and turned the initial data-collection task into a maintainable and observable data platform.
